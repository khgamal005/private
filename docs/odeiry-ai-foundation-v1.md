# أوديري — نواة المساعد الذكي v1

## الهدف

تضيف هذه المرحلة مساعد دعم داخل مساحة المنشأة يجيب عن استخدام أودير، يقترح خطوات تشخيص أولية، ويُعد مسودة تذكرة دعم. إنشاء التذكرة يظل إجراءً صريحًا من المستخدم عبر نظام الدعم القائم؛ أوديري لا ينشئها تلقائيًا ولا يغيّر بيانات المنشأة.

## حدود الإصدار

- مساعد واحد مبني على OpenAI Agents SDK مع مخرجات منظمة ومحدودة الحجم.
- معرفة منصية منسقة عن أودير فقط؛ لا تُفهرس بيانات المنشآت أو التذاكر أو المرفقات.
- سجل محادثة معزول بالمنشأة والمستخدم، وسياق شاشة مصنف دون URL أو query أو معرفات سجلات.
- قياس استخدام تجريبي `shadow` وغير قابل للفوترة؛ لا يوجد خصم أو رصيد أو محفظة في v1.
- تظل التذاكر في `core.support_requests` المصدر الوحيد للحقيقة.

## حدود الثقة والأمان

يلزم التفعيل المزدوج: `ODEIRY_AI_ENABLED=true` على الخادم، ثم تفعيل المنشأة في `core.odeiry_tenant_settings`. كلاهما مغلق افتراضيًا. مفتاح OpenAI ومفتاح Supabase السري خادميان فقط، ولا يُرسلان إلى المتصفح أو قاعدة البيانات.

تبدأ العملية بهوية جلسة المستخدم وتتحقق قاعدة البيانات من عضويته النشطة وملكيته للمحادثة. بحث المعرفة مرتبط بعملية حية ومحدود. اعتماد نتيجة النموذج وتسوية القياس يتمان عبر RPC خادمي غير متاح للمستخدمين، لمنع حقن رد أو قياس مزيف. كل جداول المنشآت تحمل `tenant_id`، وتستخدم مفاتيح مركبة وRLS مع حجب الوصول المباشر.

المحتوى القادم من المستخدم أو سجل المحادثة أو قاعدة المعرفة يعامل كبيانات غير موثوقة. لا تُعرض المراجع إلا إذا طابقت مقالًا أعادته أداة البحث فعليًا. تتطلب التذكرة مراجعة وتأكيدًا مستقلًا في الواجهة.

## دورة الطلب

1. تتحقق الواجهة من البوابة العامة وبوابة المنشأة دون تحميل وكيل الذكاء الاصطناعي عند الإغلاق.
2. يتحقق مسار الخادم من الأصل والجلسة والحجم ومعدل الطلب، ثم يحجز عملية idempotent.
3. يبحث الوكيل مرة واحدة في المعرفة المنسقة ويولد ردًا منظمًا أو مسودة تصعيد.
4. يعتمد الخادم الرد ويسجل الرموز والوحدات كقياس `shadow` غير مالي.
5. عند اختيار المستخدم إنشاء تذكرة، يرسلها المسار المعتاد `/api/support/tenant/create_ticket` بعد تأكيد صريح، ثم يسجل رابطًا idempotent بين التذكرة وعملية أوديري. فشل تسجيل الرابط لا يلغي التذكرة التي أُنشئت بالفعل.

## التهيئة والتشغيل المرحلي

لا تُطبّق الهجرة ولا تُفعّل المفاتيح أو البوابات تلقائيًا. ترتيب التشغيل الآمن:

1. تطبيق الهجرة على staging والتحقق من سجل الهجرات ومن مخطط قاعدة البيانات.
2. ضبط `SUPABASE_SECRET_KEY` و`OPENAI_API_KEY` كأسرار خادمية، مع إبقاء `ODEIRY_AI_ENABLED=false`. يقبل الخادم `SUPABASE_SERVICE_ROLE_KEY` كاسم بديل للمنشآت القائمة، مع عدم ضبط الاسمين معًا.
3. تشغيل اختبارات المصدر والبناء واختبار عزل منشأتين واختبار إنشاء التذكرة بالتأكيد.
4. تفعيل البوابة العامة، ثم تفعيل منشأة داخلية واحدة بإجراء المنصة المدقق.
5. مراقبة الأخطاء والمهلات والاستخدام، ثم التوسع تدريجيًا.

الإيقاف الفوري يتم بجعل `ODEIRY_AI_ENABLED=false`. يمكن كذلك تعطيل المنشأة منفردة. الإيقاف لا يعطل الدعم الفني اليدوي ولا يحذف أي سجل. حذف السجلات أو تحويل القياس إلى فوترة يحتاجان هجرة ومراجعة مستقلة.

## مسار التوسع

الجداول تفصل استخدام المزود عن وحدات الأعمال، لكنها لا تمنح رصيدًا ولا تسمح بالشحن. قبل أي `billable=true` يجب إضافة دفتر أستاذ مالي مستقل، تسوية خادمية موثوقة، تسعير بإصدارات، حجز/إلغاء ذري، webhooks دفع idempotent، وحدود تمنع الرصيد السالب. بعد ذلك يمكن إضافة أدوات المحتوى والدورات والتصميم ومساعد المدير كقدرات مستقلة فوق نفس بوابات العزل والتدقيق.

## قيود v1

- لا يوجد إدخال مفتاح أو تفعيل من الواجهة في هذا الإصدار.
- لا يوجد شحن وحدات أو فوترة أو تنفيذ تلقائي لمهام النظام.
- السماح بالأصل يتبع قائمة نطاقات أودير الموثوقة الحالية؛ أي نطاق مخصص يحتاج مراجعة صريحة قبل التفعيل.
- الاحتفاظ مضبوط لكل منشأة في الإعدادات، لكن تنفيذ التنظيف المؤتمت مؤجل لمرحلة منفصلة وآمنة.
