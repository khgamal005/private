# ODEIR manual tenant controls — review packet

Scope: `odeir.com`, `Marktonesa/marktone-platform-control`. Base `c03ae38640dfbf3b433be8314849d0ce4c134551`, following pricing PR #225. No Marktone CRM work. User requested manual plan assignment, tenant activation/suspension and deletion from platform control. This packet adds capability only: it does not authorize deleting or suspending any existing tenant. Publication is not performed by this branch or its CI.

## Interface

`/control/tenants` now displays state and plan without immediate onchange writes. Each row has **إدارة المنشأة**, with current identity/status/plan/member count/end date. Plan changes offer four public editions and administration-only FULL, monthly/yearly terms, before/after confirmation. The existing assignment procedure remains the source of truth. Assignment is administrative, not proof of payment, and does not reactivate a suspended workspace. Downgrades do not delete existing staff; existing hard seat enforcement limits new additions. Existing add-on rights are unchanged.

Activation and suspension are independent, confirmed operations. Subscription dates are not frozen or changed by suspension. Status is enforced by existing tenant-access functions. Delete opens the existing owner-permission preview/typed-confirmation dialog; it is NOT an unconditional purge. Financial, integration, storage, support, AI-memory and unknown-dependency blockers remain. Reef remains protected and read-only for these controls.

## Backend and safety

Two versioned RPCs return an authoritative snapshot and execute only `set_plan`/`set_status`. Require a signed-in user, distinct platform permissions, confirmed tenant identity, and an exact SHA-256 snapshot version. Lock the tenant using the same lock key as deletion and lock current subscription rows. Reject stale requests and Reef changes server-side; capture before/after audit without payment collection. No service-role key is used or exposed by the HTTP route. Requests and responses are bounded, same-origin writes required, private no-store responses, and database internals are not returned.

Pricing PR #225 introduced `catalog.core_transition_v1` with a RESTRICT tenant FK, which the older deletion preview treats as an unknown dependency. Its core terms also reference subscriptions without cascading. The forward migration narrowly reviews this one dependency and adds explicit tenant-scoped metadata cleanup AFTER the existing deletion authorization, locks, preview digest, blockers and typed confirmation. Constraints remain RESTRICT; no broad CASCADE or trigger disable. Metadata rows participate in preview freshness. Installing the migration does not delete or update any tenant/business row.

Migration filename `20260907121051_tenant_manual_controls_v1.sql` was generated by Supabase CLI `migration new` in source-audit run 34120439911. Canonical migration contains no cohort transition, new billing charge, provider call or data backfill. Existing pricing and FULL records stay unchanged.

## Verification scope and limitations

Local PostgreSQL/PGlite tests execute the new migration and RPCs with synthetic tables and fixtures for existing delegates. They verify no install-time tenant mutation; separate permission grants; anonymous and tenant-user denial; stale/unconfirmed rejection; plan/state independence; FULL assignment; Reef protection; confirmed purge cleanup; and retained financial/schema blockers. Existing independent-commerce and purge tests provide regression coverage for the delegated contracts.

Actual React/JSDOM interactions cover selection without writes, confirmation, double-submit prevention, stale-response recovery and deletion handoff. Actual route handler tests cover session/CSRF, shape validation, no-store and sanitized errors. The browser harness uses the real management and deletion components with wholly synthetic intercepted API responses, checks desktop/mobile, and uses agent-browser immediately after starting the isolated server. Temporary QA route is removed in `finally`, never committed. It does NOT prove a production authenticated transaction or real-money settlement.

A read-only attempt to invoke current production deletion previews was blocked by the tool safety check; it was not retried through a different execution route. Production mutation and production preview invocation are not part of this packet.
